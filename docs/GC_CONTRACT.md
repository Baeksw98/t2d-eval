# GC track (guideline-concordance physician validation) — data contract v2

Second track next to clinical acceptability (CA, `https://eval.asclep.org/ca/`). Entry: `https://eval.asclep.org/gc/` (own QR
`qr/gc.png`, `?src=qr`), or from the landing page `https://eval.asclep.org/` (integrated QR `qr/main.png`), which passes `src`/`site`/`wave` on.
Endocrinology board-certified specialists (내분비대사내과 분과전문의, self-reported) confirm or overturn the
**AI Rater judgments that the AI audit flagged** (△ minor error, ✗ major error with a corrected verdict). All other
AI Rater judgments were confirmed (✓) by the AI audit and are not re-checked: human-in-the-loop on the ambiguous part only.

**Separate evaluation procedure with its own backend (decided 2026-11-19):** GC has its own Apps Script project, its own
web-app URL and its own Google Sheet. The CA project/spreadsheet is not touched (CA needs no redeploy).
- `gas/Code.gs` = CA script (unchanged behaviour; rejects gc_* actions as before).
- `gas/GcCode.gs` = GC script, pasted into a NEW Apps Script project. `setup()` creates the GC spreadsheet automatically
  when no ID is set (`GC_SPREADSHEET_ID` constant or script property), creates the GC sheets, installs the 10-minute
  GC summary trigger and logs the spreadsheet URL (last log line `✅ …` or, if the trigger could not be created, `⚠️ …`).
  Both files are generated by `tools/build_gas.py`.
- GC never writes into the CA response spreadsheet: `gcSs_()` refuses a spreadsheet that has any CA sheet
  (`Responses`, `PhaseLong`, `Sessions`, `RawJSON`) — by ID or as the bound sheet — with a Korean error, and records the
  checked ID in the script property `GC_SS_CHECKED` (checked once per ID). Both projects have a sheet named `Visits`.
- Every lock is released after `SpreadsheetApp.flush()` (doPost, view beacon, summary trigger).
- `gc/gc-config.js` `ENDPOINT` = the GC web-app URL (empty until deployed → test mode).
- The CA Summary's Concordance link stays manual (copy `TargetKey` + `ConcordanceScore` from `GC_Concordance` into the CA
  `Concordance` sheet when needed).

## GC_DATA (gc/data/gc_items.js)
```
{ data_version, scope,
  units: { "<P051_gpt|P051_deepseek|P011_gpt|P011_deepseek>": {
      key, patient, model, run,
      concordance_base: { "<TargetKey>": { n, met_raw, met_ai } },   // every scored judgment of this output
      items: [ {
        id: "P051_gpt|C3|Q2.1-02"  (Phase 1: "P051_gpt|P1|Q1.1-04"),
        unit, patient, combo (0 = Phase 1, 1–3), question ("2.1" … "5.4", "1.1"/"1.2"), question_text,
        element ("Q2.1-02"), title, criterion (full 감점 기준 text),
        rater: { verdict: "met"|"deducted", type ("다루지 않음"|"틀린 권고"|""), quotes: [..], quotes_raw, reason },
        audit: { mark: "minor"(△)|"major"(✗), corrected: "met"|"deducted"|null, category, explanation, evidence: [..] },
        final: audit.corrected || rater.verdict,          // the AI pipeline's current verdict
        target_key: "P051_gpt|C3|P2" (Phase 1: "P051_gpt|P1"),
        basis (채점표 적용 근거 text, may contain 〔…〕 audit notes) } ] } } }
```
`TargetKey` = the same key CA's PhaseLong uses (`<CaseKey>|P1` or `<CaseKey>|C<n>|P<2-5>`).
`concordance_base[key]`: `n` scored judgments, `met_raw` met by the AI Rater, `met_ai` met after the AI audit.
Item counts: P051_gpt 4, P051_deepseek 8, P011_gpt 10, P011_deepseek 7 → Part A 18, Part B 11.

Blinding: never show model names, run ids, or which LLM is the Rater/auditor. Units are shown as "답변 1 / 답변 2".

## Flow (client)
1. Intro: purpose; how it works as two unnumbered lines (AI 채점; AI 감사 marks △/✗), then "선생님께서 하실 일" with the
   ①→④ reading order of the item screen (the only numbered sequence on the page, so ①–④ always mean the item steps),
   △/✗ in plain words (△ 근거 보완 = 판정은 유지하되 근거(인용·사유)에 보완이 필요하다는 의견; ✗ 판정 보정 = 판정이
   틀렸다고 보고 바로잡음, 최종 판정이 바뀜). Eligibility question (`GC_CONFIG.ELIGIBILITY`; "아니요" → blocked screen with a
   link to the CA evaluation `../ca/` and to the landing page `../`, both carrying `src`/`site`/`wave`). The intro (only) starts with
   the small site links 「처음 화면 · 벤치마크 소개」 (`../`, `../about/`, same params; never `test`/`part`/`reset`). Name (pseudonymised server-side), profile fields, consent checkbox, Part choice (A/B cards with
   item count and estimated minutes). `?test=1` → test session. `?part=A` preselects.
2. Per unit (2 per session): unit intro (patient summary, one line + the ①→④ reading order, the 3 combinations as drug
   chips; patient record in the drawer).
3. Per item — the screen reads top to bottom as a story (no outcome strip above it; the conclusion is step ④):
   - Case head pills: 답변 n · 환자, 조합 n · 답 x.y (판정 N / M is in the topbar and the dock, not repeated here).
   - **채점 항목** (context card): element id + title (`h1`), 감점 기준 clamped to 3 lines with 전체 보기
     (`opened.criterion`). The meaning of 충족/감점 is given in ④ and on the 비동의 buttons, not repeated here.
   - `<ol class="gc-steps">` with four numbered cards (`li#gcStep1…4`, badge 1–4, `h2#gcS<n>h`, joined by a connector):
     - **① CDSS 답변** — the rubric's question as quoted context ("채점표 질문 (이 답을 보는 관점)" 「question_text」, so
       it is not read as a second question to the physician), that combination's answer to the question (Phase 1: 1.1
       referral + answer / 1.2), the combination's drugs, AI 채점 quotes highlighted (yellow) and AI 감사 evidence underlined
       (green dotted). When a ②/③ quote is in another answer of the same combination (or Phase 1), that answer is shown
       right below, highlighted (`.gc-cited-row`, "AI 채점이 인용한 다른 답" / "AI 감사가 근거로 든 다른 답"), so the
       physician never has to dig for it. Expander "이 조합 전체 답변·처방 보기" / "Phase 1 전체 답변 보기"
       (`opened.full_answer`).
     - **② AI 채점 · 왜 감점했나 / 왜 충족으로 봤나** — verdict chip, 감점 유형, **판정 사유** (label kept because ③
       texts refer to AI 채점의 「판정 사유」) with the reason as the main text, then 근거로 인용한 답변: the quoted
       sentences with location notes (① 답변에 표시 / 답 x.y에 있음 · ①에 함께 표시 / 찾을 수 없음).
     - **③ AI 감사 의견** — △/✗ chip, its meaning in plain words, the explanation, 오류 유형, evidence with location notes
       (incl. "조합 n의 답 x.y에 있는 문장 · 이 화면의 답변에는 없음"). The data's word "Rater" is shown as "AI 채점"
       (Rater는 → AI 채점은, Rater가 → AI 채점이); the screen uses one vocabulary.
     - **④ 그래서 최종 판정은** — `AI 채점 판정 → 감사 반영 후 최종 판정` (= `final`); badge **감사에서 바뀜** (AI 채점 verdict
       struck) iff `audit.corrected` is set and differs from `rater.verdict`, otherwise **변경 없음**; the meaning of the
       final verdict. This is what the physician agrees or disagrees with.
   - 채점표 적용 근거 (collapsed, 참고; `opened.basis`).
   Decision dock: "**④ 최종 판정** [verdict]에 동의하십니까?" ("④ 최종 판정" scrolls to step ④) → **동의 / 비동의**.
   비동의 → choose the correct verdict among the other two of `met | deducted | not_applicable` (required), optional
   comment (encouraged). Next is enabled once complete. Small screens compact the dock as in v1.
4. Final: END_ITEMS (required), optional overall comment → submit. Done screen: send status, "다른 Part 이어서 검증"
   (continuation: same evaluator, `linked_session_id`, `session_ordinal` 2, profile + consent carried over).
   The optional JSON backup download replaces unit keys by `<patient>_답변<N>` (N = position in `order`) everywhere
   (`order`, `unit`, `item_id`, `target_key`) and sets `units_blinded: true`; Part + patient identify the unit.
Verdict wording on screen: 충족 = 감점 기준에 해당하지 않음 (no deduction), 감점 = 감점 기준에 해당함 (`VERDICTS[].hint`).
Autosave in `localStorage` (`gc:state:v1`), resume after reload, outbox with retry (same pattern as CA `app.js`).

## Payloads (client → doPost, body JSON as text/plain)
Common to `gc_start | gc_judgment | gc_finish | gc_progress`:
```
action, msg_id, client_time, study_id ("T2D-GC-2026"), app_version, data_version, instrument_version,
session_id (UUID), is_test, evaluator { name, role: "endo", eligible: true, fields {id: label}, codes {id: int} },
evaluator_id (UUID), device_id, visit_id, session_ordinal, linked_session_id, part ("A"|"B"),
sequence_index, seq_source ("server"|"local"), order [unitKey, unitKey], n_sequences,
entry { src, site, wave, part_preselected, in_app, referrer_origin }, consent { version, at, inherited }, incentive
```
`entry.referrer_origin` is the external origin of the visit. When the visit comes through the landing page `/` or `/about/`,
`document.referrer` on `/gc/` is this site, so `gc.js` uses the origin those pages stored on entry in `sessionStorage['t2d:entry_ref']`
(`''` = direct). Visitors who leave on the landing page send no beacon.
- `gc_start`: + `device{…}` (same shape as CA). Response `{ ok, seq_index }` (balanced within the Part).
- `gc_judgment`: + `judgment` (below). Sent when the evaluator presses 다음 on an item (re-sent on edit; upsert).
- `gc_finish`: + `judgments[]` (all), `end_items {id: {value, code}}`, `overall_comment`, `session {started_at,
  finished_at, total_active_ms, total_wall_ms, resumes, send_failures}`, `device{…}`.
- `gc_progress`: + `progress { furthest_unit, furthest_item, items_done, last_activity_at }`. Fire-and-forget (sendBeacon).
- `view` beacon for the intro page (`study_id` GC, `entry.src`) → `Visits` sheet of the GC spreadsheet.

`judgment`:
```
item_id, unit, unit_order (1|2), item_order (1-based within session), patient, combo, question, element,
audit_mark, audit_category, rater_verdict, audit_corrected, ai_final,
agree (bool), phys_verdict ("met"|"deducted"|"not_applicable"; = ai_final when agree), comment,
answered_at, item_ms (visible), active_ms, ttfd_ms (time to first decision), changes,
opened { criterion, full_answer, basis, patient } (bools)
```

- **GC_Judgments** (one row per session × item, upsert):
  `ServerUpdatedAt, SessionId, IsTest, EvaluatorName, EvaluatorCode, EvaluatorId, Part, SequenceIndex, SessionOrdinal,
  UnitOrder, ItemOrder, UnitKey, PatientId, Model, Combo, Question, Element, ItemId, TargetKey, AuditMark,

  (`PhysVerdict = AIFinal`). `ClientMismatch` (blank = consistent) records a payload whose `data_version`, `ai_final` or

  `ItemSec`, `ActiveSec`, `Changes`, `Opened*` are the session's cumulative values for the item: at submission for
  completed sessions (the `gc_finish` copy updates them even when the verdict is unchanged, never lowering a value),
  otherwise at the item's last 다음. `TTFDSec` = time to the first decision.

## Adjudication + summary (`buildGcSummary`, run by the GC project's 10-minute trigger `refreshGcSummaryIfDirty` when real GC data changed)
Per flagged item, physician verdicts from non-test, non-pilot GC_Judgments (one per physician, latest wins):
- Pilot sessions (`Wave` starting with `pilot`, link `?wave=pilot`) count in the participation flow [1] only, as in CA.
- Physician = `EvaluatorCode` (normalised name) → else `EvaluatorId` → else `SessionId`. If one code has ≥ 2
  `EvaluatorId`s whose `Eval_*` profiles differ, each `EvaluatorId` is a separate physician (`G001-1`, `G001-2`, in order
  of first appearance). Same profile + the same item on two devices → one physician (latest wins) but listed under
  "동명이인 의심" in GC_Summary [0]; same profile, different items (e.g. Part A on phone, Part B on PC) → normal.
- n = 0 → `대기` (AI final kept). A verdict with a strict majority (> n/2) → adjudicated = that verdict;
  `확정(만장일치)` if n ≥ 2 and unanimous, `확정(다수결)` if n ≥ 3 and majority, `잠정(1인)` if n = 1.
  No verdict with a strict majority → `추가 검토 필요` (AI final kept): ties, an n = 2 split, and a three-way split where
  the most frequent verdict is not > n/2 (e.g. 2·1·1 of 4).
- Adjusted counts per TargetKey: start from `concordance_base` (`met_ai`, `n`); for each item whose adjudicated verdict
  ≠ AI final: met↔deducted moves one between met/deducted; `not_applicable` removes it from n (and from met if AI final
  was met).
Sheets written:
- **GC_Adjudication**: one row per flagged item: ItemId, UnitKey, Element, Title, Combo, Question, AuditMark,
  AuditCategory, RaterVerdict, AIFinal, N, AgreeN, Met, Deducted, NotApplicable, Adjudicated, Status, Comments
  (`G001: …` joined).
- **GC_Concordance**: TargetKey, N_AI, Met_Raw, Met_AI, Score_Raw, Score_AI, N_Adj, Met_Adj, ConcordanceScore
  (= Met_Adj / N_Adj, 4 decimals), FlaggedItems, Adjudicated, Pending. Same `TargetKey` as CA PhaseLong, so it can be
  pasted into the CA `Concordance` sheet.
- **GC_Summary**: participation flow (visits, eligible/ineligible not tracked server-side, sessions by status and Part,
  physicians n), [2] validator characteristics (board_years, setting, ai_freq, Parts, Src, FormFactor), per-item table,
  [4] agreement of physicians with AI audit final vs raw AI Rater (overall, by ✗/△ — named as on the item screen,
  "✗ (판정 보정)" / "△ (근거 보완)" — by audit category; Wilson 95% CI),
  [4-2] item-level agreement, **[4-3] AI 사용 빈도별 AI 최종 판정 동의율** (automation-bias check: one row per `ai_freq`
  level in code order 1–5, then `(미응답·기타)` if any, then 전체; columns `AI 사용 빈도 (ai_freq), 코드, 전문의 n, 판정 n,
  AI 최종 동의 n, AI 최종 동의율, 95% CI 하한, 95% CI 상한`; same judgments as [4] — non-test, non-pilot, one per physician
  × item (latest); a physician's level = `Eval_ai_freq` of their first session that has it; Wilson CI per level, with a
  note that judgments cluster within physicians), inter-physician agreement (percent agreement; Fleiss κ when every item in
  a Part has the same n ≥ 2), score table per output (Phase 1, Phase 2–5, per combination: raw Rater → AI audit →
  physician-adjudicated), time per item (median, IQR), END_ITEMS distribution.
- **GC_Codebook**: Sheet, Column, Description, Type / values, InSheet for every GC sheet (incl. dynamic `Eval_*` / `End_*`).
The GC data needed server-side (item metadata, concordance_base) is embedded in `gas/GcCode.gs` as `GC_ITEMS` by
`tools/build_gas.py` reading `gc/data/gc_items.js` (single source of truth; no copy-paste). The same build copies the
sheet/summary helpers GC uses from `gas/src/*.gs` by name (never CA entry points or triggers); tests: `node tools/test_gc.js`.

## Timestamps and reset (GC backend v3, 2026-11-20)
Same rule as CA: columns ending in `At` (incl. `AnsweredAt`) hold date-time values shown as `yyyy-mm-dd hh:mm:ss`, time zone
`Asia/Seoul`. `resetAllGcResponses()` backs up the spreadsheet, clears Visits / GC_Sessions / GC_Judgments / GC_Raw to their
headers, resets G-codes and Part sequence counters, and rebuilds the GC summary sheets.
